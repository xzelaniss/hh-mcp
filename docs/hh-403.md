# Диагностика 403 при поиске вакансий: hh-mcp.onrender.com

Проверено 9 ноября 2026 г. (Москва). Исправление подготовлено для ветки
`security/self-hosted-oauth`; автоматического развёртывания эта инструкция не делает.

## Проверенные факты

| Проверка | Результат |
|---|---|
| GET `https://hh-mcp.onrender.com/health` | 200: `status=ok`, `tools=19`, `version=2.1.0` |
| POST `/mcp` без Bearer | 401 с OAuth `resource_metadata` — защита включена |
| `HeadHunter.validate_token` через установленный плагин | `HH_ACCESS_TOKEN` не задан |
| `HeadHunter.get_areas_subtree` с `area_id=1` через тот же плагин | `1 — Москва` — MCP/OAuth и исходящий запрос к HH работают |
| `HeadHunter.search_vacancies` (`python`, Москва, `per_page=1`) | Ошибка инструмента с **ответом API hh.ru 403**, `errors: [{type: "forbidden"}]` |
| Такой же анонимный GET `https://api.hh.ru/vacancies?...` из среды диагностики | 403 с тем же типом ошибки; три корректных варианта User-Agent не изменили результат |

HH request_id воспроизведения через Render: `1794177364056354d42f87d2c9641008`.
Без параметров поиска ошибка также воспроизведена:
`17941774246902869541f87c8f085004`.

**Источник наблюдаемого 403 — hh.ru API, а не собственный OAuth MCP.**
Успешный `/health` проверяет только процесс, а не доступ к поиску hh.ru.
В старом коде любой upstream 403 заменялся пояснением
`token lacks required scope`, хотя в реальном ответе нет ни `oauth`, ни кода scope.
Это была выдуманная классификация. Сырой ответ HH `forbidden` сам по себе не
устанавливает, что заблокирован именно IP Render, User-Agent или конкретный scope.

## Нужен ли HH-токен для «публичных» вакансий

Вакансии публичны на сайте, но это не означает неограниченный анонимный API.
Актуальная [операция get-vacancies](https://api.hh.ru/openapi/redoc#tag/Poisk-vakansij/operation/get-vacancies)
прямо говорит: **«Если не передан токен авторизации, то после первого запроса
будет предложено пройти капчу»**. Это же указано для поиска похожих вакансий.
В официальной [таблице методов](https://github.com/hhru/api#vacancies) для поиска
указаны режимы приложения/работодателя, а не гарантированный anonymous.

Поэтому единичный анонимный запрос может работать; код не запрещает такой запрос.
Но устойчивый серверный поиск следует настроить с легитимным **токеном приложения HH**.
Предыдущие заявления проекта «поиск всегда без токена, токен нужен только для резюме»
исправлены. Для резюме по-прежнему нужен именно пользовательский токен работодателя
и оплаченный доступ; токен приложения не даёт этих прав.

Собственный OAuth ChatGPT — другой слой. Его access token нельзя отправлять в HH.
Добавление `HH_ACCESS_TOKEN` не требует отключать OAuth или пересоздавать его секреты.

## Что исправлено в коде

- 403, captcha, неверный User-Agent, ошибка HH OAuth и платные права различаются
  по документированным `errors[].type/value`, без угадывания scope.
- Ошибка инструмента содержит безопасный `structuredContent.error`:
  `source=hh_api`, `http_status`, `reason`, `endpoint` без query, `authorization`
  (`anonymous` или `hh_token`) и `request_id`, когда HH его предоставил.
- Upstream 403 остаётся `isError=true` внутри нормального ответа MCP; не превращается
  в транспортный отказ собственного OAuth. В тесте проверен HTTP 200 MCP с ошибкой HH 403.
- Сырые HH body/HTML, descriptions и captcha URL/state не передаются модели и в логи.
- `HH_ACCESS_TOKEN` очищается от внешних пробелов и отправляется только в HH;
  префикс `Bearer` хранить в env не нужно. Некорректные значения/переносы отвергаются
  без раскрытия значения. Redirect исходящего API-запроса не разрешён.
- `HH_USER_AGENT` применяется к обоим исходящим заголовкам одинаково; CR/LF и
  не-ASCII отвергаются. HH отдаёт приоритет `HH-User-Agent`, если переданы оба.
- `validate_token` сначала выполняет минимальный поиск **с сервера Render**, затем
  проверяет `/me`, если HH-токен задан. Приложение не обязано иметь профиль `/me`:
  отказ этого метода после успешного поиска больше не означает «токен истёк».

Все 19 имён инструментов, собственный OAuth, PostgreSQL и публичный `/health` сохранены.
Нет автоматических повторов 401/403, смены IP, обхода капчи или подмены браузерного UA.

## Действия владельца перед развёртыванием

1. На [dev.hh.ru/admin](https://dev.hh.ru/admin) создайте/выберите своё приложение,
   получившее требуемый доступ HH. Если требуется согласование HH, дождитесь его.
2. Если токен приложения уже выдан, посмотрите его в административной панели и
   сохраните приватно. Если он ещё не выдавался, получите его **один раз** по
   [официальной процедуре](https://github.com/hhru/api/blob/master/docs/authorization_for_application.md):
   `POST https://api.hh.ru/token`, `Content-Type: application/x-www-form-urlencoded`:

   ```text
   grant_type=client_credentials
   client_id=<ID ВАШЕГО ПРИЛОЖЕНИЯ HH>
   client_secret=<СЕКРЕТ ВАШЕГО ПРИЛОЖЕНИЯ HH>
   ```

   Отправляйте запрос приватным локальным HTTP-клиентом с вашим User-Agent;
   из ответа нужен `access_token`. Это **не** OAuth Client ID/Secret MCP из Render.
   Не присылайте значения в чат и не добавляйте их в GitHub.
   Повторный выпуск токена приложения отзывает ранее выданный токен. Не помещайте
   выпуск в Build/Start Command, cron или перезапуск Render. Это не выполняется PR.
3. В Render → сервис **hh-mcp → Environment** добавьте:
   - `HH_ACCESS_TOKEN` = полученный HH `access_token`, без `Bearer`, кавычек и переносов;
   - `HH_USER_AGENT` = настоящее имя/версия вашего приложения и ваша контактная почта,
     например `my-hh-mcp/1.0 (you@example.com)` (замените пример своим контактом).
4. Не изменяйте `MCP_AUTH_MODE=oauth`, DB URL, пароль владельца, MCP Client Secret,
   callback URI или `HH_ALLOWED_HOSTS` ради исправления upstream 403.
   `HH_ALLOWED_HOSTS` для этого сервиса — `hh-mcp.onrender.com`, без схемы/пути.
5. Оставайтесь на Render Free. Сохраните Auto-Deploy = Off. Слияние и Deploy —
   отдельные действия после подтверждения владельца.

## Развёртывание исправления после подтверждения

PR направлен **в `security/self-hosted-oauth`**, поскольку Render использует эту ветку.
После одобренного слияния PR убедитесь, что Render → Settings → Branch указывает на неё.

| Поле | Значение |
|---|---|
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `node dist/index.js --http` |
| Health Check Path | `/health` |
| Node | `NODE_VERSION=24` |
| Auto-Deploy | Off |

После согласования выберите **Manual Deploy → Deploy latest commit**. Если сохранение
Environment предлагает **Save, rebuild, and deploy**, это тоже запускает развёртывание:
нажимайте только после разрешения. Не добавляйте секреты в команды/логи сборки.
Проверьте SHA развёрнутого commit в Render; версия `/health` остаётся 2.1.0 и сама
по себе не доказывает, что обновлён именно код диагностики.

После прогрева `/health` обновите инструменты плагина в настройках ChatGPT
(Refresh/Обновить), чтобы подтянуть новое описание `validate_token`.
Пересоздавать OAuth-подключение обычно не нужно: добавление HH-токена не меняет
версию собственного OAuth и не отзывает MCP-сессии.

## Приёмка и если поиск всё ещё запрещён

1. Попросите ChatGPT вызвать именно **HeadHunter → validate_token**.
   Новая версия проверит минимальный `/vacancies` из того же процесса/IP Render.
2. Ожидается «Поиск вакансий с HH_ACCESS_TOKEN успешно проверен» или валидный
   пользователь `/me`. Для токена приложения отсутствие `/me` нормально.
3. Выполните `search_vacancies` с `text=python`, `area=1`, `per_page=1`, `page=0`.
4. Если осталось `source=hh_api, http_status=403, authorization=hh_token`:
   - `invalid_hh_token` → исправить/обновить HH-токен согласно конкретному коду HH;
   - `bad_user_agent` → проверить настоящее значение HH_USER_AGENT;
   - `captcha_required` → HH требует капчу; не автоматизировать обход;
   - `hh_permission_required` → проверить роль/приобретённый доступ данного метода;
   - общий `forbidden` → уточнить доступ приложения и обратиться в поддержку
     HH с **request_id и временем**, попросив проверить ограничения приложения/egress IP.
     По одному этому коду нельзя достоверно назвать причину «IP заблокирован».
5. При транспортном 401 `/mcp` заново пройдите собственный OAuth; это другая проблема.
   Транспортный 403 с `Invalid Host header` относится к `HH_ALLOWED_HOSTS`, а не HH API.

Проверка из вашего ноутбука не доказывает доступность с Render: исходящие IP разные.
На Render Free нет Shell, поэтому проверка встроена в уже защищённый `validate_token`;
нового публичного диагностического endpoint нет.

**Граница выполненной проверки:** реальный анонимный отказ воспроизведён через
ваш плагин и отдельным API-клиентом. Автотесты воспроизводят его и успешный запрос
с отдельным HH application token на имитации API. Реальный HH-токен владельца
не предоставлялся, поэтому живой поиск с ним пока не проверен и не обещается
исправленным одним обновлением кода. Настройка настоящего HH-токена обязательна
для проверки устойчивого доступа; generic forbidden после неё разбирает HH.
